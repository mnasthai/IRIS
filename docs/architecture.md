## 🧱 1. 设计约束

IRIS 本质运行在**别人家的进程里**，这决定了几乎全部设计：

| 约束 | 后果 |
| :--- | :--- |
| 崩溃的是微信，不是我们 | 任何一次内存访问都必须有硬件异常兜底 |
| Hook 跑在微信的热路径上 | 观测代码不能阻塞、不能分配、不能抛异常 |
| 微信是重度多线程 + Qt | 核心对象有线程亲和性，只能在它自己的 UI 线程上碰 |
| 版本一变全部失效 | 所有 RVA 集中管理，并做三重校验后才挂钩 |
| DLL 可能被卸载 | 工作线程与静态状态必须能安全存活到进程结束 |

## 🚀 2. 进程模型与注入

采用经典**远程线程注入**，由 `launcher` 完成：

```
OpenProcess
  → 解析本进程 LoadLibraryW 及其宿主模块（得到相对偏移）
  → 轮询等待目标进程加载同一宿主模块，按偏移算出远程 LoadLibraryW 地址
  → VirtualAllocEx + WriteProcessMemory 写入 DLL 路径
  → CreateRemoteThread 执行 LoadLibraryW
  → Toolhelp 快照轮询确认 DLL 真正进入模块表
```

两个不显然的点：

- ** `LoadLibraryW` 在 `kernel32.dll`。** 现代 Windows 上它可能被转发到 API Set，因此用 `GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS)` 反查真正的宿主模块，再按"本地函数地址 − 本地模块基址"求偏移，避免跨进程地址错位。
- **确认模块已挂载，而不是只等远程线程返回。** `CreateRemoteThread` 返回不代表加载器已把模块登记进 Toolhelp 模块链表，因此注入后额外做模块探测，并区分"模块不存在"与"快照本身失败"。

## 🧷 3. DllMain 纪律

`DllMain` 处于加载器锁保护下，此刻做任何可能阻塞或间接加载 DLL 的事都会死锁。因此：

- `DLL_PROCESS_ATTACH`：只调用 `DisableThreadLibraryCalls`，再 `CreateThread` 派生主线程，**立刻返回**；
- `DLL_PROCESS_DETACH`：**只置停机标志**，不 Join、不卸载 Hook、不释放句柄。

所有重量级初始化都在 `ObserverThread` 中完成。

### 🧿 只注入主进程

微信桌面端是多进程架构（主进程、渲染子进程、GPU 进程、崩溃处理器）。若不区分，所有子进程都会加载本 DLL 并争抢同一份管道与日志。判定条件是：

- 模块文件名恰为 `Weixin.exe`，**且**
- 命令行不含 `--type=`，且不含 `--crashpad-handler`

## 🎯 4. 目标校验

挂钩前做三重校验，任一不符即拒绝初始化并输出 `observer_disabled`：

1. **文件版本** —— 从 `Weixin.dll` 读取版本资源，四段版本号必须与 Profile 声明的完全一致；
2. **PE 标识** —— DOS/NT 头签名、`Machine` 为 AMD64、`SizeOfImage` 等于 Profile 中记录的预期镜像大小；
3. **函数入口特征码** —— 逐个比对入口点前若干字节的机器码指纹。

前两项由 `VerifyTarget` 在启动时完成；第三项分散在各 Hook 安装点，未匹配的观测点会被**单独跳过**而不是拖垮整个后端（接收路径除外，它是必需的）。

> [!NOTE]
> 这样设计的用意：逆向偏移在版本漂移时最危险——**偏移错了不会报错，只会读到垃圾或崩溃**。把版本、镜像尺寸、机器码三层绑在一起，可以让绝大多数不匹配在挂钩前就被拦下。

## 🪝 5. Hook 链

| 观测点 | 必需 | 说明 |
| :--- | :--- | :--- |
| 批量接收消息 | ✅ | 后端核心，失败即整体终止 |
| 发送信令请求 | ❌ | `WECHATBOT_SEND_TRACE` |
| 发送上下文构造 | ❌ | `WECHATBOT_SEND_CONTEXT_TRACE` |
| 原生提交函数 | ❌ | `WECHATBOT_SEND_SUBMIT_TRACE` |
| 媒体下载完成 | ❌ | `WECHATBOT_MEDIA_RECEIVE` |

### 🧼 透传纪律

Hook 函数必须做到"观测之后原样放行"：

- **保存并恢复 `GetLastError`**。观测代码内部会调用大量 Win32 API，若不恢复，调用方会看到被污染的 `LastError`；
- **不改动任何入参、寄存器与返回值**；
- Hook 体内的异常绝不向外传播（原函数本身抛出的异常除外，那属于调用方的正常语义）。

`HookReceiveBatch` 是这套纪律的样板：进入时存 `LastError` → 解包 → 恢复 `LastError` → 调用原函数 → 再存结果 `LastError` → 排队返回事件 → 恢复 → 返回原函数结果。

## 🛡️ 6. 内存安全模型

读取微信内部结构是最高危的部分。防线是分层的：

1. **可读性探针** —— 每次解引用前用 `IsReadableRange` 确认地址区间真的可读；
2. **类型指纹** —— 比对对象的虚表指针是否等于"模块基址 + Profile 中的虚表 RVA"。这一步能识别出"内存可读但根本不是这个类型"的情况；
3. **存在位图** —— Protobuf 风格结构体用 `_has_bits_` 标记字段是否被发送。**`has_bits` 为 0 的字段不是"空值"，而是"不存在"**，必须分别处理；
4. **硬件异常兜底** —— 上述检查之间仍可能存在竞态（例如另一线程正在释放对象），因此真正的解引用包在 `__try / __except` 里。

任何一层失败都只丢弃**当前这一条**消息并记录诊断状态，绝不向上传播异常、绝不让微信崩溃。

> [!IMPORTANT]
> 这也是**必须使用 MSVC**的原因：`__try / __except` 是 MSVC 扩展，GCC / Clang 不支持。

### 🔤 字符串读取

微信的字符串是 SSO（小字符串优化）布局：短字符串内联在对象里，长的走堆指针。读取器按 SSO 规则判断走向后再读取，并对三个边界做处理：

- **按 UTF-8 码点边界截断**，绝不切断多字节字符；
- 区分"空字符串"与"字段不存在"；
- 无效 UTF-8 单独标记，不捕获任何字节。

## ⚡ 7. 事件模型与热路径

事件对象是一个 `std::variant`，按事件类别选择载荷。两条强约束：

```cpp
static_assert(std::is_trivially_copyable_v<Event>);
static_assert(std::is_trivially_destructible_v<Event>);
```

即**无需析构、可平凡拷贝**。原因有二：

- 事件对象要穿过 `__try / __except` 边界，其间不允许有 C++ 展开义务；
- 观测路径上不允许出现堆分配与所有权转移。

载荷使用**固定容量缓冲**（`CapturedText<N>`），把"字节数 + 读取状态 + 内容"绑在一起传递，包括内嵌 NUL 与被截断的 UTF-8。

### 🔁 环形队列

观测线程与刷盘线程之间是一个固定 256 槽的环形队列，由 SRW 锁保护：

- 生产者用 `TryAcquireSRWLockExclusive`，**拿不到锁就直接丢弃并计数**，绝不阻塞热路径；
- 队列满同样丢弃并计数；
- 丢弃计数会被周期性写成 `dropped` 事件。

丢弃是有意的：让微信卡住比丢掉一条诊断信息严重得多。

### 💰 一个需要注意的代价

> [!WARNING]
> `Event` 的变体里最宽的载荷是发送提交快照（含引用快照的多个 512 字节字段与数 KB 文本），使单个 `Event` 达到数十 KB 量级。256 槽静态数组因此占用数 MB 的进程地址空间。这是"热路径零分配"换来的代价，微信进程的内存占用会相应增加。

## 🧵 8. UI 线程调度

> [!IMPORTANT]
> **这是发信能否工作的关键。** 微信基于 Qt，其网络与消息对象有强烈的线程亲和性：在后台线程直接调用原生发信函数会崩溃或死锁。

`UiDispatcher` 的做法是把闭包送回微信自己的 UI 线程执行：

1. 用 `EnumWindows` 找到类名为 Qt 主窗口类的窗口，取其线程 ID；若发现多个不同线程持有同类窗口，**放弃绑定**（防止投递到错误的子线程）；
2. `SetWindowsHookEx(WH_GETMESSAGE)` 挂到该线程；
3. 用 `RegisterWindowMessage` 注册一个全局唯一消息；
4. `PostThreadMessage` 投递带任务令牌的消息；
5. 微信消息泵取出消息时，Hook 回调执行对应闭包；
6. 用事件对象同步等待完成。

### 🚦 状态机

每个任务经历 `pending → running → done`，或 `pending → cancelled`。调用方等待结果时，超时分支必须区分两件事：

| 结果 | 含义 |
| :--- | :--- |
| `cancelled_before_start` | 任务在 UI 线程取出前被取消，**无副作用**，可安全重试 |
| `timeout_after_start` | 任务**已开始执行**但调用方等超时。副作用可能已发生，**严禁自动重试** |

> [!WARNING]
> 这个区分是刻意保留的：把"没发出去"和"不知道发没发出去"混为一谈，会导致重复发送。

### 🧩 其它细节

- 若调用线程本身就是目标 UI 线程，直接内联执行，避免给自己投消息造成死锁；
- 卸载 Hook 时**绝不持有自身状态锁**，否则会与 Windows 的系统回调互相等待；
- 任务令牌单调递增且不回绕，用于识别陈旧消息。

## 📤 9. 发信路径

分层清晰，每层职责单一：

```
命名管道 → HandleCommand → SendGate → SendService → UiDispatcher
                                                     ↓
                                              原生对象构造与提交
```

### 🚧 `SendGate`：安全门禁

所有发信指令的第一道关。校验项按顺序包括：时间窗、开关状态、幂等去重、账号一致性、目标白名单、媒体/引用/@ 参数合法性、发送模式约束、并发与频率冷却。

它同时负责**幂等**：以 `request_id` 为键缓存结果，完全相同的重复请求直接返回原结果而不重新执行。

### 🎛️ `SendService`：编排

- **耗时 IO 放在工作线程**：媒体文件的校验、哈希计算都在调度前完成，绝不占用 UI 线程；
- **派发前二次校验**：指令可能在队列里排队，因此真正提交前会重新校验时间窗、账号与执行器状态；
- **在途任务租约（`ActionLease`）**：用引用计数实现停机屏障，即使任务超时或异常，计数也能准确归零，不会让停机永久阻塞；
- **图片句柄驻留**：微信是异步上传图片的，因此在提交前把图片文件的句柄加入驻留表，防止上传期间文件被外部删除或改写。

### 🧬 `native_text`：原生调用生命周期

文本发送要在微信堆上构造一整套原生对象（字符串源、延迟任务持有器、元数据、回调可调用体），再调用提交入口。这里最棘手的是**所有权追踪**：

- 原生函数通过出参返回对象，**只有正常返回后才归调用方所有**。因此状态机区分 `未进入 / 已进入未返回 / 已返回` 三种情况——中途抛异常时所有权不明，此时**不可贸然析构**；
- 析构带独立的"已进入析构"状态，严格防重复释放。

引用回复更复杂：需要构造一个原始消息对象，交给原生转换器提炼出引用结构，**逐字段比对内存镜像与预期一致**后才附加到待发送消息上。这一步的比对是必要的——如果引用数据构造错了，发出去的是错误的引用卡片，而不会有任何报错。

## 🛑 10. 停机与生命周期

停机是**逆序且有预算**的：

| 顺序 | 动作 | 理由 |
| :--- | :--- | :--- |
| 1 | 停止命名管道 | 不再接受新指令 |
| 2 | 等待原生发信空闲 | 确保已进入微信的任务安全返回 |
| 3 | 停止媒体接收管线 | 不再产生新的落盘任务 |
| 4 | 停止日志线程并排空 | 把已排队的事件全部写完 |
| 5 | 关闭日志文件 | 最后一步 |

> [!IMPORTANT]
> 任何一步在超时预算内没完成，**不强行析构**，而是保留资源并每秒重试，直到全部干净退出。

### 🕳️ 刻意的内存泄漏

> [!NOTE]
> 几处单例（日志状态、管道状态、媒体管线、UI 调度注册表、原生发信后端）都采用 `new` 分配且**永不释放**。
>
> 这不是疏忽：DLL 卸载期间 CRT 静态析构的顺序不可控，而已进入 UI 线程的任务可能仍持有指向这些状态的指针。让它们随进程一起消失，比在错误的时机析构安全得多。

> [!WARNING]
> 同理，**不要对 `IRIS.dll` 调用 `FreeLibrary`**——工作线程会访问已卸载的代码页。

## 🧾 11. 版本 Profile

所有与微信版本绑定的常量集中在 `include/monitor/config/profiles/` 下的单个头文件中：

- 函数入口 RVA 与虚表 RVA
- 结构体大小、字段偏移、`_has_bits_` 位掩码
- 函数入口的机器码指纹
- 预期镜像大小
- 全局对象指针与账号信息提取链的偏移

编译期通过 `version_profile.hpp` 选择 Profile 并导出统一的常量名。新增版本支持 = 新增一个 Profile 头文件 + 切换别名，**不改动任何业务代码**。

## ⚖️ 13. 已知取舍

- **单任务 UI 调度**：同一时刻只允许一个任务派发到 UI 线程，并发请求返回 `busy`。换取了状态机的简单与可验证。
- **管道单实例短连接**：实现简单、无连接状态管理，代价是每次请求一次连接建立。
- **事件队列不可配置**：256 槽是固定值。溢出会丢事件并告警，但不提供扩容开关，避免在热路径上引入动态容量。
- **DLL 与进程同生命周期**：不支持运行中卸载重载。
- **无自动重连**：UI 线程若被重建，绑定不会自动恢复，发信能力会持续不可用直到重启流程。
